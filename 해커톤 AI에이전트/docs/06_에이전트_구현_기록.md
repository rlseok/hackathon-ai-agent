# 06. 에이전트 구현 기록 (2026-10-16, 노트북)

노트북(RTX 5060 Laptop 8GB, RAM 16GB, Python 3.11, Ollama + qwen3:8b)에서 05 문서의 뼈대를 실제 에이전트로 만든 기록.
각 단계마다 **무엇을 / 왜 / 결과**를 적는다.

---

## 실행 방법

```
.\.venv\Scripts\Activate.ps1
streamlit run app.py                         # 대시보드형 화면 (브라우저 http://localhost:8501)
streamlit run app_chat.py --server.port 8503 # 채팅형 화면 (http://localhost:8503, 오른쪽 작업 패널)
python -m agent.pipeline --showcase          # 화면 없이 우수 사례 일괄 실행
python -m agent.pipeline <사진> --domain msdd --lang vi   # --lang ko | vi | en
python -m agent.pipeline --inbox             # inbox/pcb, inbox/msdd 사진 일괄 검사
```
결과: `outputs/inspection_ledger.xlsx`(엑셀 대장), `outputs/records/`(md), `outputs/abnormal/`(관리자 보고서), `outputs/second_inspection/`(검수 요청서).
`outputs/` 폴더를 지우면 기록이 초기화된다.
Ollama 가 실행 중이어야 한다 (작업 표시줄 트레이 또는 `ollama serve`).

## 전체 구조

```
[app.py 화면] 사진 선택/업로드 → [검사 시작]
   │
   ▼  agent/pipeline.analyze()
① detect.py     YOLO 검출 (큰 사진은 타일링) → 결함별 정상/의심/이상 판정 + 판정 근거
② knowledge.py  taxonomy YAML 조회 → 원인·조치, 대표 유형, 전면 분포·복합 결함·부품 단위 상황
④ writer.py     Qwen 이 주어진 사실로만 보고서 문장 작성 (한국어 / 베트남어)
   │
   ▼  화면: 작업자가 유형·판정 수정 → refresh(), 문장 편집, 에이전트에게 질문(chat.py)
   │
   ▼  finalize() / reject_false_positive()
이상 → outputs/abnormal/*_defect_report.docx (관리자용)
의심 → outputs/second_inspection/*_inspection_request.docx (작업자용)
정상 → 보고서 없음
오탐 기각 → 정상 처리 + outputs/retraining/normal/ 에 사진 보관
모두 → outputs/inspection_ledger.xlsx + outputs/records/<날짜>/*.md
```

역할 분담 원칙(01 문서)은 그대로: **보는 것은 YOLO, 판정·절차는 코드, 문장·설명은 Qwen**. Qwen 은 판정을 바꿀 수 없다.

## 단계별 기록

### 1. 파이프라인 (agent/detect, knowledge, writer, report, pipeline)

- **결정:** 원인 후보 '목록'은 YAML 원문을 코드가 넣고, Qwen 은 설명 문장만 쓴다 → 작은 모델이 원인을 지어내는 것을 막음.
  물리적 조치 문장에는 코드가 "[작업자 확인 후 실시]"를 강제로 붙인다.
- **수정:** 대표 유형 동점 처리(심각도 → 최고 신뢰도 → 검출 수), taxonomy 의 영문 용어 한글화.

### 3. 정상 / 의심 / 이상 3단계 판정
- **왜:** 오탐이 그대로 관리자 보고서가 되면 신뢰를 잃는다. 확실한 것만 관리자에게, 애매한 것은 작업자 2차 검수로.
- **규칙 (YAML `judgment.rules`, 코드 수정 없이 변경 가능):**

| 모델 | 이상으로 올림 | 의심으로 내림 |
|---|---|---|
| PCB | 단락·단선·홀 누락: 신뢰도 0.35부터 | 스크래치·핀홀: 항상 |
| 금속 | 접힘: 0.25부터 / 기공·스크래치: 전면 분포 | 국부 기공·스크래치, 0.5% 미만 흑점, 0.6 미만 산화, 얼룩 |

- **결과:** showcase 14장 → 이상 10 / 의심 3 / 정상 1. 금속 부품 13개 중 검사자 OK 부품을 '이상'으로 올린 경우 5 → 2.
- **추정값:** 흑점 0.5%, PCB 0.35 는 근거 데이터 없이 정함 → `msdd_v1` 라벨과 meta.csv 검사자 OK/NG 로 재조정 필요.

### 4. 작업자 확인 화면 (app.py, Streamlit) — 1단계
- **한 것:** 예시 사진(우수 사례) 선택 또는 업로드 → 판정 배지·이상/의심 수·대표 유형 → 표시 이미지 →
  결함 표에서 유형·판정 수정(제외=오탐) → [수정 반영] → 보고서 문장 편집 → [확정] 보고서 생성·다운로드 / [오탐 기각].
- **구조 변경:** `pipeline.run()` 을 `analyze → refresh → finalize` 로 나눔. 작업자가 고친 뒤에 보고서를 만든다.
- **확인:** 브라우저에서 PCB·금속 예시 검사 → 확정 → `outputs/abnormal/` 보고서 생성까지 확인.

### 5. 한국어 / 베트남어 — 2단계
- **한 것:** 화면 문구(`agent/i18n.py`), 보고서 두 종류의 제목·표·안내, 판정 근거 문장, 위치 표기, Qwen 문장을 언어별로.
  YAML 에 `name_vi`(유형명), `note_vi`(2차 검수 확인 방법) 추가. 베트남어 문장 작성 시 용어집(동박=lá đồng 등)을 프롬프트에 넣음.
- **결정:** 베트남어 보고서에서는 한국어 지식베이스 원문 목록을 빼고 Qwen 이 번역한 문장만 넣는다 (한국어 혼입 방지).
- **확인:** 화면을 Tiếng Việt 로 바꿔 금속 사진 검사 → 베트남어 불량 분석 보고서 생성 확인.
- **주의:** qwen3:8b 의 베트남어는 어색한 표현이 있을 수 있다 (예: 동박을 '시계'로 오역한 적 있어 용어집 추가). **FPT 팀원 검토 필요.**

### 6. 에이전트 대화창 (agent/chat.py) — 3단계 (Q&A)
- **한 것:** 화면 오른쪽에서 Qwen 에게 질문. 지금 검사 결과·지식베이스를 프롬프트에 넣어 그 근거로만 답하고, 답을 스트리밍으로 표시.
  빠른 질문 버튼 3개(왜 이 판정? / 원인은? / 지금 뭘 확인?).
- **안전장치:** 판정 변경 요청에는 "제가 바꿀 수 없으니 결함 표에서 수정하거나 [오탐 기각]" 으로 답하도록 고정. 근거 밖 질문은 모른다고 답함.
- **확인:** "왜 이 판정이야?" → 전면 기공 근거로 설명. "정상으로 바꿔줘" → 거절하고 화면 수정 안내.

### 7. 검사 기록 — 엑셀 검사 대장 + md 요약 (agent/records.py)
- **왜:** Word 보고서는 이상·의심일 때만 나오는 정식 문서라 여러 건을 비교·집계하기 어렵다. 관리자는 엑셀이 익숙하고,
  md 는 사람이 읽기 쉬우면서 대화창이 과거 사례를 찾는 자료가 된다.
- **한 것:** 검사할 때마다(분석 직후 '작업자 확인 대기', 확정 후 최종 상태로 갱신)
  - `outputs/records.jsonl` 원본 기록 (같은 검사는 마지막 줄이 최신)
  - `outputs/inspection_ledger.xlsx` 매번 다시 생성, **영어**. 시트: **Inspections**(썸네일, 판정 색, 품번·공정·로트, 처리 상태, 보고서·md 링크) /
    **Defects**(결함 1개 = 1줄, 판정 근거) / **Summary**(날짜별 정상·의심·이상, 유형별 건수, 확인 대기 수)
  - 기록에는 언어와 무관한 값(도메인·판정·대표 유형·공정 코드, 결함별 클래스·판정·근거 키)을 함께 저장해 영어 문구를 만든다.
    화면 언어와 상관없이 대장은 항상 영어 (어디서나 읽을 수 있게). 처음엔 한국어 `검사대장.xlsx` 였다.
  - `outputs/records/<날짜>/<검사id>.md` 판정·결함 표·원인·조치·표시 이미지 링크 (검사 언어로 작성)
- 엑셀을 열어 둔 채 기록되면 `inspection_ledger_<시각>.xlsx` 로 따로 저장하고 화면에 경고.
- 기존 `이력.csv` 는 이걸로 대체했다.

### 8. 부품 정보 분리 + 대기함 일괄 검사
- **부품 정보:** 품번 / 공정(선택 목록: 가공·열처리·표면처리·세척·식각·도금·드릴·조립·포장·기타) / 로트를 따로 입력.
  보고서·Qwen 프롬프트·검사 대장에 각각 들어간다. 나중에 공정별 원인 좁히기, 품번·로트별 반복 결함 추적에 쓴다.
- **대기함:** `inbox/pcb/`, `inbox/msdd/` 에 사진을 넣고 화면의 [일괄 검사] (또는 `python -m agent.pipeline --inbox`).
  - 사진은 `outputs/received/<날짜>/` 로 옮겨 처리 (같은 사진 중복 검사 방지)
  - 금속은 파일명의 부품번호로 묶어 부품 단위 판정
  - 정상 → 자동 통과 기록 / 의심·이상 → '작업자 확인 대기' 목록 → 화면에서 [열기] → 확인·수정 → 확정
- **확인:** 브라우저에서 대기함 2장 일괄 검사 → 이상 1·의심 1 → 의심 건 열어 확정 → 대기 목록 6→5, 대장 상태 갱신 확인.

### 9. 영어 화면·보고서
- 화면 문구, 보고서 두 종류, 판정 근거, 처리 상태, 위치 표기, 공정 이름을 영어로. YAML 에 `name_en`, `note_en` 추가.
- Qwen 이 한국어 프롬프트에 끌려 한국어로 쓰는 문제가 있어, 프롬프트 맨 끝에 대상 언어로 "모든 값을 영어로" 를 다시 지시.
- 면적을 숫자(0.48)로 주면 Qwen 이 48% 로 읽는 오류가 있어 `"0.48%"` 처럼 단위를 붙여 넘기도록 수정.
- 검사 대장 엑셀은 관리용이라 한국어로 고정, md 와 보고서는 검사 언어로.

### 10. 화면 구조 변경
| 위치 | 내용 |
|---|---|
| 우측 상단 | 🌐 언어 버튼 → 누르면 한국어 / Tiếng Việt / English 선택 |
| 본문 상단 [검사 입력] | 검사 대상, 사진(예시·업로드·대기함), 품번·공정·로트, 케이스·사진 선택, [검사 시작] / [일괄 검사]. 결과가 열리면 접힌다 |
| 본문 | 판정·사진·결함 표·보고서 문장·처리 + 오른쪽 에이전트 대화창 |
| 좌측 사이드바 [검사 대장 · 기록] | 보기(확인 대기 / 전체 / 이상 / 의심 / 정상), 검색(파일·부품번호·품번·로트), 기록 목록(🔴🟠🟢, ⏳=확인 대기) → 누르면 본문에 열림, 엑셀 대장 다운로드 |
- 확인 대기 기록을 열면 이어서 확인·확정하고, 처리 끝난 기록을 열면 결과와 보고서·md 다운로드를 볼 수 있다.
- 처음에는 표(dataframe)의 행 선택으로 만들었으나 체크박스가 작아 누르기 어려워, 한 번 누르면 열리는 버튼 목록으로 바꿨다.

### 11. 화면 두 가지 — 대시보드형 / 채팅형
같은 기능을 두 가지 배치로 만들어 비교·시연용으로 고를 수 있게 했다. 공통 부품은 `ui.py` 에 모아 두 화면이 같은 동작을 한다.

| | 대시보드형 `app.py` | 채팅형 `app_chat.py` |
|---|---|---|
| 실행 | `streamlit run app.py` (8501) | `streamlit run app_chat.py --server.port 8503` |
| 가운데 | 검사 입력 → 검사 결과 | **대화창**: 📎 사진 첨부 / 📷 예시 / 📥 대기함, 결과는 대화에 카드로 남음 |
| 오른쪽 | 지금 검사에 대한 대화창 | **작업 패널**: 카드를 누르면 열림. 결함 표 수정·문장 편집·확정 |
| 좌측 | 검사 대장 · 기록 (같음) | 검사 대장 · 기록 (같음) |
| 어울리는 쓰임 | 반복 검사·현장 작업 | 시연, 처음 쓰는 사람, 질문이 많은 경우 |

- 채팅형에서도 **검사·판정은 코드가 고정 절차로** 하고, 판정 수정·확정은 작업 패널에서만 한다. Qwen 은 질문 답변만.
  대화 속 예전 카드는 "열기" 버튼만 있고 편집 칸이 없어, 어떤 검사를 고치고 있는지 헷갈리지 않는다.
- 확인: 채팅형에서 예시 검사 → 카드·작업 패널 표시 → "왜 이 판정이야?" 답변, 대시보드형에서 대장 기록 열기.
  **📎 파일 첨부 검사는 브라우저 자동화로 파일 선택 창을 열 수 없어 직접 확인하지 못했다.**

### 12. 보고서 미리보기 후 저장
- **한 것:** [불량 보고서 미리보기] / [2차 검수 요청서 미리보기]를 누르면 **실제로 저장될 Word 문서를 임시로 만들어 HTML 로 바꿔**
  미리보기 창(팝업)에 띄운다. [저장]을 눌러야 `outputs/abnormal/` 또는 `outputs/second_inspection/` 에 저장되고 검사 대장에 기록된다.
  [돌아가서 수정]을 누르면 창이 닫히고, 결함 표나 문장을 고친 뒤 다시 미리보기를 연다. 정상 처리는 확인 창만 뜬다.
- **왜 HTML 변환인가:** 화면용으로 따로 그리면 실제 문서와 달라질 수 있다. 같은 docx 를 `mammoth` 로 변환해 "보이는 그대로 저장"되게 했다.
- 두 화면(대시보드형·채팅형) 모두 같은 `ui.decision()` 을 써서 똑같이 동작한다.
- **확인:** 대시보드형에서 확인 대기 건 열기 → 미리보기 창(제목 7개 절, 표 6개, 이미지 7장) → [저장] → 처리 완료·다운로드 버튼, 대장의 확인 대기 목록에서 빠짐.

### 13. 채팅형: 오른쪽 작업 패널 + 대화로 보고서 수정
- **왜:** 보고서를 보면서 고칠 문장을 긁어(복사) 채팅에 붙이고 "이렇게 고쳐줘"라고 요청하려면, 보고서가 대화와 따로 떠 있어야 한다.
- **구조:** 작업 패널이 **좌측 사이드바처럼 화면 오른쪽에 고정**되어 대화와 따로 스크롤된다 (`ui.right_panel_css`, `ui.work_panel`).
  - 패널을 열면 가운데 대화 영역과 아래 입력창이 왼쪽으로 비켜나고, 도구 버튼은 아이콘 위주로 줄어든다.
  - 패널 머리의 ⇔ 로 넓게(60%)/보통(44%), ✕ 로 닫기. 도구줄의 🛠 버튼으로 다시 연다. 검사하거나 기록을 열면 자동으로 열린다.
  - 패널 안: **보고서** 탭(저장될 문서 그대로, 드래그·복사 가능) / **편집·확정** 탭(결함 표 수정, 문장 편집, 미리보기·저장, 오탐 기각).
  - 처음에는 작업창을 브라우저 새 창(/work)으로 만들었으나, 같은 화면 안의 오른쪽 패널이 맞다는 의견에 따라 바꿨다.
- **수정 요청 흐름:** 채팅에 "고쳐줘·바꿔·줄여·change·sửa…" 같은 말이 있거나 ✏️ 수정 요청을 켜면 →
  Qwen 이 바꿀 필드만 JSON 으로 제안(`agent/chat.py: propose_edit`) → 채팅에 이전(취소선)/새 문장과 [적용]/[취소] →
  [적용]하면 결과에 저장되고 작업 패널 보고서가 바로 바뀜. 판정·결함 정보는 대화로 바꿀 수 없다 (패널의 결함 표에서).
- **자동 저장:** 작업 패널(과 대시보드형)에서 결함 표·문장을 고치면 바로 결과 파일에 저장된다. 화면을 닫아도 고친 상태로 이어진다.
- **확인:** 기록 열기 → 오른쪽 패널 열림(고정, 패널 안 스크롤) → 보고서/편집 탭 전환 → ✕ 로 닫으면 대화 영역이 다시 넓어짐.
  수정 요청 → [적용] → 보고서 갱신은 새 창 방식에서 확인한 같은 코드다.

### 14. 채팅형: 질문 안내 상자
- **왜:** 대화창에서 무엇을 물어볼 수 있는지 모르면 쓰기 어렵다. 질문하기 전에 짧게 알려 준다.
- **한 것:** 검사 결과가 열리고 아직 질문하지 않았으면 입력창 위에 **"이렇게 물어보세요"** 상자가 뜬다.
  - 6가지: 🔎 판정 이유 / 📍 결함 내용 / 🧪 원인 / 🛠 조치·확인 / 🌐 다른 언어로 / ✏️ 보고서 문장 수정. 각 줄의 예시를 누르면 바로 질문이 보내진다.
    원인 예시에는 대표 결함 이름이 들어간다 (예: "단선은(는) 왜 생겨?").
  - 아래에 안 되는 것(판정 변경, 다른 검사·과거 기록 조회, 지식베이스 밖 내용)을 한 줄로 알린다.
  - 첫 질문을 하면 접히고, [알겠어요 (닫기)] / [다시 보지 않기] 로 닫을 수 있다. 언제든 입력창 위 **❓** 버튼으로 다시 볼 수 있다.
- **확인:** 단선 기록 열기 → 상자 표시 → "왜 이 판정이 나왔어?" 누름 → "치명 결함이라 기준 0.35 를 넘어 이상" 답변.
  스크래치 기록 열기 → "결함이 어디에 몇 개 있어?" → 답변 후 상자 접힘.

### 15. 화면 안내(투어) — 두 화면 모두
- **왜:** 처음 쓰는 사람이 각 영역이 무엇을 하는지 바로 알 수 있게 (일반 서비스의 첫 사용 안내처럼).
- **한 것:** `tour.py`. 단계마다 해당 영역을 빨간 테두리로 강조하고 나머지를 어둡게 한 뒤, 설명 카드에 [◀ 이전] [다음 ▶] [건너뛰기].
  - 대시보드형 11단계: 소개 → 언어·가이드 → 검사 대장 → 검사 입력 → 판정 → 원본·결함 위치 → 결함 표 → 보고서 문장 → 처리 → 대화창 → 마무리
  - 채팅형 10단계: 소개 → 언어·가이드 → 검사 대장 → 도구 → 대화 → 입력창 → 작업 패널 → 보고서 탭 → 편집·확정 탭 → 마무리
  - 검사 결과가 필요한 단계에서 열린 검사가 없으면 검사 대장의 최근 기록을 예시로 연다 (채팅형은 작업 패널도 자동으로 연다).
  - 이 컴퓨터에서 화면을 **처음 열 때 자동으로 시작**하고 (`outputs/.tour_seen_dash`, `.tour_seen_chat` 로 기억),
    이후에는 제목 옆 **🧭 가이드** 버튼으로 다시 본다. 세 언어 지원.
  - 영역 표시는 `st.container(key=...)` 의 `st-key-*` 클래스로 한다 (`tour_lang`, `tour_input`, `tour_verdict`, `tour_photos`,
    `tour_table`, `tour_text`, `tour_decision`, `tour_chat`, `tour_toolbar`, `tour_chatbox`, `tour_inputrow`, `work_panel`).
- **확인:** 두 화면에서 첫 실행 시 자동 시작, 모든 단계를 넘기며 오류 없음, 강조 영역으로 자동 스크롤, 건너뛰기 후 다시 안 뜸.
  확인 후 표시 파일을 지워 두어, 사용자가 처음 열 때 다시 자동으로 뜬다.
- **보완 (언어 먼저 · 카드가 따라 움직임):**
  - 첫 단계에서 안내 언어를 고른다 (한국어 / Tiếng Việt / English 버튼). 고른 언어가 화면 언어가 되고 이후 안내도 그 언어로 나온다.
    단계 수는 대시보드형 12, 채팅형 11.
  - 카드는 강조 영역 옆의 빈 자리로 옮겨 다닌다: 오른쪽 → 왼쪽 → 아래 → 위 → 네 구석 중 **강조 영역을 가장 덜 가리는 곳**,
    왼쪽 사이드바 위는 피한다. 스크롤·창 크기 변경 때 다시 계산하고, 강조 영역이 화면 밖이면 먼저 보이게 스크롤한다.
  - Streamlit 1.66 은 본문 블록이 fixed 위치의 기준점이 되어 좌표가 어긋나므로, 카드를 놓은 뒤 실제 위치를 재서 차이만큼 보정한다.
  - 확인: 대시보드형 영어 안내 전 단계에서 강조 영역이 화면에 보이고 카드와 겹침 0% (검사 입력 단계만 5%),
    채팅형 베트남어 안내에서 작업 패널 단계는 카드가 패널 왼쪽에, 대화 단계는 오른쪽 아래 구석에 놓임.
- **재작성 (끊김·박자 어긋남 해결):** 단계마다 서버가 페이지 전체를 다시 그리던 방식이라 화면이 깜빡이고, 강조 테두리와 카드가
  따로 움직였다. 안내를 **브라우저 안에서만 도는 오버레이**(`tour_overlay.js`)로 바꿨다.
  - 서버(`tour.py`)는 언어 고르기 창(st.dialog)과 단계 문구만 준비해 한 번 넘기고, 이후 [다음]·[이전]·[건너뛰기]·키보드(←, →, Esc)는
    브라우저에서 처리 → 페이지를 다시 그리지 않는다.
  - 강조 영역(spot)과 카드는 같은 계산에서 함께 위치가 정해지고, 단계가 바뀔 때만 0.35초 부드럽게 이동, 평소에는 스크롤을 매 프레임 그대로 따라간다.
  - 화면 전체(사이드바 포함)를 한 겹으로 어둡게 하고 강조 영역만 뚫는다. 아래쪽 진행 점(●○○)으로 위치를 보여준다.
  - 채팅형은 입력창이 화면 하단 고정이면 Streamlit 이 페이지를 계속 맨 아래로 붙여 위쪽 영역 안내가 밀려났다 →
    입력창을 대화창 바로 아래(일반 위치)로 옮겨 해결.
  - 확인: 두 화면 모든 단계에서 강조 영역이 화면 안, 카드와 겹침 0%. 단계 사이에 창 크기 변경 이벤트를 넣어도 유지.

  - 정상 기판: 결함 자리를 **같은 기판에서 둘레 무늬가 가장 비슷한 깨끗한 부분으로 복사**해 메운다(마스크 템플릿 매칭).

### 20. 실시간 검사 — 영상 서버 + 실시간 화면 + 기존 에이전트 연결 (2026-10-21)
- **구조:** 카메라(또는 가상 컨베이어 영상)를 여는 곳은 **영상 서버 하나**(`live/server.py`, 포트 8506)뿐이다.
  화면들은 서버가 내보내는 영상(MJPEG)과 현황(JSON)을 받아보기만 하므로 몇 개를 열어도 카메라 충돌이 없고 검사도 한 번만 한다.
  ```
  영상(파일 반복 / 웹캠) → [영상 서버] ─ 미리보기(매 프레임, 화면 전체 YOLO, 얇은 박스)
                                       ├ 센싱 구역(가운데 640×640): 기판 중심이 지나는 순간 1번 정식 검사 → 판정 도장 OK/HOLD/NG
                                       ├ 판정 이벤트 → 보고 에이전트(큐) → 지식 조회 + Qwen 초안 → 검사 대장 '작업자 확인 대기'
                                       └ 판정 이벤트 → 라인 감시 에이전트 → 경고
            ├ /stream.mjpg ─ 실시간 화면 app_live.py (8505) · 전용 뷰어 http://localhost:8506/ (프로젝터)
            └ /state ─ 카운트, 최근 판정, 경고, 보고서 상태
  ```
- **기판 찾기:** 회색 벨트 위 초록 영역(G − max(R, B) > 25)의 열 분포로 기판 위치를 찾는다. 판정이 붙은 기판은 이 위치를 따라 도장·박스가 같이 움직인다.
- **센싱:** 기판 중심이 화면 가운데를 지나는 프레임에서 640×640 을 잘라 `agent.detect.detect` 로 검사 → 기존과 같은 판정 규칙·기준값. 캡처는 `outputs/live/captures/`.
- **보고 에이전트:** `pipeline.analyze_detected` (YOLO 를 다시 돌리지 않고 지식 조회·문장 작성만) → `register_pending` (출처 `source: live`).
  Qwen 은 한 건에 약 12초, 기판은 약 2초마다 오므로 대기가 2건을 넘으면 AI 문장 없이 바로 대장에 기록(이상은 4건까지 AI 우선). 문장은 대시보드의 [문장 다시 생성]으로 쓸 수 있다.
  Qwen 이 쓰는 동안은 미리보기를 2프레임에 한 번으로 줄여 영상이 끊기지 않게 한다.
- **라인 감시 에이전트 (규칙):** 같은 위치 반복(최근 5장 중 3장, 지식 파일 repeated_location) > 연속 불량 4장 > 같은 유형 반복(최근 5장 중 3장) > 최근 불량률 90% 이상.
  기판 하나에 경고는 하나만, 같은 종류는 8장 동안 다시 내지 않는다.
- **검사 대장 동시 기록:** 대시보드·채팅·영상 서버가 같은 대장에 쓰므로 `records._Lock`(잠금 파일 `outputs/.ledger.lock`)으로 순서를 맞춘다.
  실시간 기록은 jsonl·md 만 바로 쓰고, 엑셀(썸네일 포함, 몇 초 걸림)은 영상 서버가 20초마다 모아서 다시 만든다.
- **실행:** 바탕화면 "불량분석 에이전트 - 실시간 검사 (시연)" 또는 `launch_demo.ps1 -App live` → 영상 서버(8506) + 실시간 화면(8505).
  웹캠: `python -m live.server --camera 0`. 화면의 ⏸/⏮/↺ 로 일시정지·처음부터·집계 초기화, 언어를 바꾸면 보고서 문장 언어도 바뀐다.
- **확인 (RTX 5060 노트북):** 30fps 유지, 프레임당 처리 약 18~30ms. 첫 35장 판정이 영상 json 의 예상과 35/35 일치.
  대시보드 검사 대장에 실시간 건이 '작업자 확인 대기'로 올라오고, 열면 사진·판정·재검사 의뢰서 미리보기가 나온다.
- **참고:** 시험 실행으로 검사 대장에 실시간 기록 100줄이 들어가 있다 (`source: live`, 이름 `live_…`). 시연 전에 정리 가능.

### 25. 실시간 라인은 기록만, 보고서 문장은 열 때 작성 (단계 1-1, 2026-10-21)
- **왜:** Qwen 은 한 건에 3~7초(처음 불러올 때 약 11초), 제품은 약 2초마다 온다. 라인에서 바로 쓰면 대기열이 밀리고 GPU 를 나눠 써 미리보기도 느려진다.
- **영상 서버 (`live/server.py`):** 기록 에이전트가 기본으로 Qwen 을 부르지 않는다. 판정·결함·캡처·지식 조회만 대장에 '작업자 확인 대기'로 기록하고
  문장은 비워 둔다(`text.pending_ai`). 예전처럼 바로 쓰려면 `--write-now` (그때만 `--max-backlog` 적용).
- **열 때 작성 (`ui.open_record` → `write_on_open`, 대시보드·채팅 공통):** 확인 대기 기록이 의심·이상인데 문장이 없으면 그 자리에서 Qwen 이 작성
  ("실시간 라인 기록입니다 — Qwen 이 보고서 문장을 작성하는 중…"). 결과·대장 md 를 갱신하고, 실패하면(Ollama 꺼짐 등) 경고만 띄우고 기록은 그대로 연다.
  대장의 검사 시각은 바꾸지 않는다 (`records.upsert(when=…)`).
- 실시간 화면·뷰어의 상태 문구: "대장에 기록 (보고서는 열 때 작성)" (3개 언어).
- **확인:** 금속 라인 35초 — 28.9fps, 대기열 0, 26건 중 이상 14·의심 8 모두 'logged', 정상 4.
  채팅 화면에서 이상 기록 열기 → 작성 중 표시 → 요약 "기공이 전면 분포하여 …" 와 작업 패널 (Qwen 첫 로드 포함 약 20초).
  대시보드에서 의심 기록 열기 → 요약 작성, 시각 21:54 유지. 시험 기록 28줄은 `tools/clear_live_records.py` 로 정리.
- **참고:** 작업 중 노트북의 Microsoft Store 판 Python 이 시작 단계에서 멈추는 문제가 있었다 (`python -c print(1)` 도 멈춤). 실제 재시작(전원 → 다시 시작)으로 해결.
  대회 노트북에서 같은 일이 생기지 않도록 python.org 판 Python 3.11 로 바꾸는 것을 권장.

### 26. 실시간 화면의 오류 기록 → 채팅 화면 작업 패널로 바로 열기 (단계 1-3, 2026-10-21)
- **실시간 화면 (8505):** 최근 판정 목록의 이상·의심 항목마다 **💬 채팅에서 열기** 링크 (새 탭, 화면 언어를 함께 넘김). 정상은 링크 없음.
- **전용 뷰어 (8506):** 이상·의심 항목 카드 전체가 같은 링크 (마우스를 올리면 테두리). 주소의 호스트를 그대로 써서 8503 으로 연다.
- **채팅 화면 (8503):** 주소 `?open=<기록 id>&lang=ko|vi|en` 으로 열면 그 기록을 검사 대장에서 찾아 오른쪽 작업 패널에 연다 (`app_chat.open_from_link`).
  보고서 문장이 아직 없으면 1-1 과 같이 그 자리에서 Qwen 이 쓴다. 대화에 "실시간 라인에서 연 기록입니다…" 와 결과 카드가 남고, 편집 탭부터 보인다.
  주소의 open·lang 은 바로 지워 새로고침해도 다시 열지 않는다. 링크로 온 경우에는 화면 안내(투어)를 띄우지 않는다.
  기록이 아직 대장에 없으면(판정 직후 아주 잠깐) "잠시 후 다시 눌러 달라"는 안내만 남긴다.
- **확인:** 금속 라인 15초 → 실시간 화면 링크 5개 → 첫 링크(이상) 클릭 → 채팅 화면에서 작성 중 표시 → 작업 패널(편집 탭), 요약 작성, 대장 목록에서 해당 기록 강조.
  뷰어(?lang=vi)는 이상·의심만 링크(정상은 그대로), 링크 언어 vi. 없는 id 로 열면 베트남어 안내. 시험 기록은 정리함.

  - 크기는 라인 영상과 같다: PCB 640×640, 금속 512×512, 액정 960×540. json 은 기존 형식 + `domain='mixed'`, `sizes`, 제품마다 `domain`·`board_w/h`.
  - 벨트는 짙은 파랑 한 색. 회색은 금속면·휴대폰 배경과 겹치고, 초록·검정은 PCB·금속 배경과 겹친다. 짙은 파랑은 액정 라인에서 검증됐다. 제품 사이 간격 200px, 속도 16px/프레임.
- **분배 에이전트 — 규칙 기반 (`agent/line_router.py`):**
  - 먼저 Izumi 브랜치(`feat/auto-router-rag-data-audit`)의 `agent/router.py` 를 GitHub 에서 읽어 검토했다. DINOv2 특징 + 로지스틱 회귀 구조인데
    timm·scikit-learn·joblib 패키지와 `models/router_backbone.pt`·`router.joblib` 가 더 필요하다. 새로 받지 않는 조건이라 가져오지 않았다.
  - 대신 영상 서버가 찾은 제품 상자(벨트 색과 다른 영역)의 겉모양으로 정한다: ① 가로세로비 ≥ 1.4 → 액정 ② 초록 비율 ≥ 0.15 → PCB ③ 어두운 비율 ≥ 0.15 → 금속 ④ 그 밖 → 크기가 가장 가까운 종류.
  - 기준값은 혼합 영상 90개의 분포에서 정했다:

| 특징 | PCB | 금속 | 액정 |
|---|---|---|---|
| 상자 크기 (px) | 640×640 | 512×512 | 932~960 × 496~540 |
| 가로세로비 | 1.00 | 1.00 | 1.73~1.94 |
| 초록 비율 | 0.74~0.91 | 0.00 | 0.00 |
| 어두운 비율 (최대 채널 < 50) | 0.02~0.14 | 0.21~0.55 | 0.55~0.82 |

  - 액정도 어둡지만 가로세로비가 먼저 가리고, PCB 는 초록이 먼저 가린다. 여유가 커서 카메라 조명이 바뀌어도 버틸 것으로 본다 (실제 카메라에서는 다시 재 볼 것).
- **영상 서버 `--line mixed`** (기존 pcb/phone/metal 동작은 그대로):
  - 제품 찾기는 같은 '벨트 색과 다른 영역'. 갈라진 제품 잇기(`_join`)는 틈은 가장 작은 제품(512)의 25%, 이은 폭은 가장 큰 제품(960)의 115% 기준.
  - 센싱 순간 분배 에이전트가 종류를 정하고 → 그 종류의 크기로 잘라 → `detect(그 종류)` → 판정·기록. 기록 에이전트는 그대로 (결과의 domain 이 제품마다 다름 → 보고서 지식도 그 종류 것).
  - 도장에 종류를 붙인다 (`#12 HOLD LCD`, `NG PCB`, `OK METAL`). 세 모델은 시작할 때 미리 올린다.
  - 미리보기: 화면 전체에 세 모델을 돌리지 않고, 아직 판정 전이고 화면에 다 들어온 제품 중 센싱 구역에 가장 가까운 하나만 분배 에이전트로 종류를 정해 그 모델 하나로 본다.
  - 정답 대조(`compare`)는 제품마다 정답의 크기를 쓰고, 분배가 맞았는지(`routed_ok`, `route_acc`)도 센다. 대조 기록 csv 에 `gt_domain, domain, route_rule` 열 추가 (혼합 라인만).
  - 왼쪽 끝으로 나가며 잘린 제품은 보이는 부분의 가운데가 아니라 오른쪽 끝에서 위치를 잡는다 — 액정처럼 넓은 제품의 결함 박스가 오른쪽으로 밀리던 것 (혼합 라인만 적용. 액정 라인에도 같은 현상이 있지만 기존 동작은 바꾸지 않음).
